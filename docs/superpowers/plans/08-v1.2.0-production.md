# 单节点生产交付阶段（v1.2.0）

目标不是把所有“以后可能需要”的基础设施提前建完，而是把当前判定引擎
收束成一个边界清楚、可部署、可备份、可验证的单节点服务。

## 阶段一：入口身份

- 生产环境必须同时配置 console key、console approver identity、agent key
  map 和 approver key map，缺一项拒绝启动。
- 控制台支持 HttpOnly cookie 登录、CSRF token 和 `X-Console-Key` 兼容入口。
- agent key 只能操作绑定身份的会话；approver key 只能审批，不信任请求体
  自报的审批人。

验收：未认证请求返回 401，缺失 CSRF 返回 403，越权返回 403。

## 阶段二：请求边界与可观测性

- 限流、流式请求体上限、`X-Request-ID`、逐行 JSON 访问日志。
- `/healthz` 只表示进程存活；`/readyz` 检查数据库、策略和商城；失败时返回
  可解析的 JSON。
- 生产日志使用专用 stdout formatter，避免容器日志前面混入非 JSON 前缀。

验收：chunked body 不能绕过大小限制，非法 `Content-Length` 返回 400，
限流返回 429，日志可被日志系统按 JSON 行消费。

## 阶段三：数据完整性与隐私

- SQLite 启用 WAL、`busy_timeout` 和 `synchronous=NORMAL`。
- 审计写库前对邮箱、手机号、正文、账户号和凭证类字段做递归脱敏，脱敏值
  参与哈希链计算。
- 计划与审批表保留执行所需原始参数；生产必须使用加密卷和 API 鉴权，不能
  把审计脱敏误写成“所有业务表都不留存敏感数据”。
- `maintenance` 清理过期会话和终态业务记录；审计链不自动截断。
- `audit-anchor` 生成外部链头 JSONL，`verify --anchor-file` 检测尾部截断。

验收：脱敏后原文不进入审计库；外部锚点能发现被删除的最后一条；
保留期命令不删除审计记录。

## 阶段四：部署与恢复

- K8s 清单固定单副本、单 worker、`Recreate`，网关与商城各自使用 PVC。
- Ingress 终止 TLS；容器以非 root 用户、只读根文件系统运行。
- 镜像 tag 固定，不使用 `latest`；策略随镜像版本发布和回滚。
- 备份优先使用卷快照；恢复时缩容到 0，先恢复旧版本，再升级。

验收：manifest 结构可校验，`/readyz` 与探针可工作，备份恢复和镜像回滚
路径写入部署说明。

## 阶段五：证据收口

- 全量测试、ruff、三套评测、bench 和生产配置启动冒烟测试通过。
- README、系统设计、部署说明和 limitations 使用同一套边界：单节点试点
  可用，多副本高可用未交付。

验收：`pytest`、`ruff`、`guardrail eval*`、`guardrail bench` 均通过；生产
变量启动后能验证 401、429、`/healthz` 和 `/readyz`。

## 明确留在后续

| 项 | 理由 |
|---|---|
| 多副本共享状态 | SQLite 是单写者；需要先实现外置会话与审计存储 |
| 跨副本全局限流 | 当前限流是单进程状态 |
| 会话 kill switch | 需要常驻控制面和全局会话索引 |
| 审批通知与升级 | 需要 webhook/邮件/值班路由，属于控制面产品 |
| 策略热加载 | 当前以镜像版本为发布边界，先保证可回滚而不是可热改 |
| OTel 与多租户 | 不影响单节点试点正确性，分别属于观测和多租户路线 |

这份阶段划分只描述交付边界，不把未实现能力写成“预留即完成”。
